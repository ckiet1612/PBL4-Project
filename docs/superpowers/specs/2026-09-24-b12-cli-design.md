# B12 CLI Design

## Goal

Build the product `nexa` CLI as a REST client for the existing Nexa API contract. The CLI must cover the approved B12 user and `SYSTEM_ADMIN` command capabilities, preserve backend authorization and state ownership, and leave the existing `nexa-maintenance` executable unchanged.

## Scope and Boundaries

The CLI owns local configuration, profile and tenant selection, scoped bearer-token loading, bounded file streaming, retry decisions, output formatting, and stable exit-code mapping. The API remains the only authority for tenant membership, ownership, scopes, roles, state transitions, quotas, idempotency records, leases, fences, and recovery.

The CLI will not access PostgreSQL, Docker, server artifact paths, or worker/internal endpoints. B15 controls such as cancel, pause, resume, manual retry, quarantine, and recovery control are excluded. No scheduler, Web UI, GPU, multi-server, or release implementation is added.

## Architecture

The product entry point is `src/nexa/cli/app.py`; `src/nexa/cli/main.py` remains the maintenance entry point. Typer command modules call `NexaClient` and do not contain HTTP transport or authorization logic.

The modules have these responsibilities:

- `client.py`: endpoint resolution, HTTP requests, bearer and tenant headers, bounded timeout and retry policy, streaming request/response handling, response headers, and contract error decoding.
- `config.py` and `storage.py`: XDG profile/config and credentials resolution, precedence, permission checks, atomic writes, and secret redaction. They do not import FastAPI, SQLAlchemy, or domain services.
- `errors.py`: typed CLI errors and exit codes 0 and 2 through 10.
- `output.py`: stable JSON output and human output; successful data goes to stdout and diagnostics to stderr.
- `idempotency.py`: secure key generation and request replay metadata without persisting secrets.
- `commands/`: Typer-only user and admin command handlers grouped as config, token, artifact, job, and admin. Template and other unwired surfaces remain unregistered.

The client maps commands directly to the operation IDs and paths in `docs/contracts/openapi.yaml`. It never infers permissions from command names or local profile data.

## Command Coverage

The root exposes `config`, `token`, `artifact`, `job`, and `admin` groups. The
registered surface covers token metadata lifecycle, artifact upload/list/get/
download, job submit/list/get/session/events/result/result-download, and admin
tenant/user/membership/global-policy/tenant-policy/audit operations whose
FastAPI routes exist in the current snapshot. Contract operations without a
backend route or service are deliberately not registered until their API
integration evidence exists.

The CLI will not expose the B15 control operation IDs `cancelJob`, `pauseJob`, `resumeJob`, or `retryFailedJob`.

## Configuration and Credentials

Configuration uses `$XDG_CONFIG_HOME/nexa` or `~/.config/nexa`:

- `config.toml` stores profiles, endpoint, active profile, and non-secret tenant context.
- `credentials.json` stores tokens only when the user explicitly chooses to persist them.

The directory is created with mode `0700`; files are written atomically with mode `0600`. Resolution precedence is command flag, then environment, then the active profile. The endpoint, profile, and tenant may be supplied by flags. Raw tokens are never accepted by a `--token` option, written to `config.toml`, included in logs or errors, or printed by `config show`. Supported token sources are credentials storage, a dedicated environment variable, and stdin.

`token create` persists a raw token only after receiving the first successful response and validating its metadata. A transport failure after server commit retries with the same idempotency key when the request body is replayable; a `one_time_secret_unavailable` response never creates a second token and reports the server metadata location without exposing a secret.

## HTTP, Retry, and Idempotency

`httpx` is the transport dependency already present in the locked environment. Requests use bounded connect/read/write/overall timeouts and bounded exponential backoff. `Retry-After` is honored for retryable dependency and rate-limit responses. GET/list/read operations may retry within the bound. Mutations retry only when they carry a stable idempotency key and the body can be replayed safely. File uploads reopen the local file for a retry; non-seekable streams do not retry after consumption.

Every mutation accepts `--idempotency-key`; absent keys are generated with a cryptographically secure random source. The same key is reused across a replay attempt. Admin mutations also pass `--if-match` byte-for-byte when required by the contract and never substitute a wildcard or silently refetch a newer version.

Tenant context is sent as the contract's `X-Nexa-Tenant-Id` header. The CLI never changes it implicitly and never treats `SYSTEM_ADMIN` as tenant membership or as permission to impersonate another user.

## Artifact I/O

Uploads read local files in bounded chunks, calculate exact SHA-256 and byte size, and send the four artifact headers plus `Content-Type: application/octet-stream`. The response metadata is checked against the local declaration. Downloads stream to a staging file, support one contract-approved byte range, verify checksum/size/ETag when present, fsync the file and parent directory, then atomically rename. Existing output is rejected unless `--force` is provided; failed downloads remove staging files. Server paths and redirects are never surfaced.

## Output and Errors

`--output human|json` is available globally. JSON output has deterministic key ordering and contains only successful response data on stdout. Human output includes the fields needed for submit and administrative workflows. Binary downloads never share stdout with diagnostic text.

Errors include the contract error code, HTTP status, request ID, and a bounded next action. Exit codes are 2 for local syntax/input, 3 authentication, 4 authorization or tenant context, 5 missing resources, 6 conflicts including idempotency and ETag, 7 rate limiting, 8 network/dependency failure, 9 other API errors, and 10 integrity/checksum failure. Messages omit tokens, passwords, SQL, tracebacks, server paths, input content, and checkpoint content.

## Testing and Evidence

Implementation follows TDD. Unit tests cover config precedence and permissions, secret redaction, output and exit codes, error decoding, timeout/retry and `Retry-After`, idempotency reuse, ETag forwarding, cursor/page bounds, and bounded checksum-verified file I/O. Contract tests use a transport or ASGI client to assert method, path, query, body, headers, tenant context, and operation mapping.

PostgreSQL/API integration tests cover upload, submit, job/session/event/result reads, result download, idempotency replay and response loss, token response loss, tenant isolation, exact scope denial, admin read/write separation, stale ETag, pagination bounds, and checksum verification where the current server routes exist. The evidence document will distinguish these checks from contract-only commands whose backend route is not yet wired.

The current FastAPI application wires B06 through B11 operations, but does not
yet wire all B12 read/admin paths such as template, attempts, checkpoints,
logs, progress, and several worker/fairness/recovery endpoints. The CLI keeps
those operations out of the command surface until backend routes/services and
API integration evidence exist; it does not create backend substitutes.
